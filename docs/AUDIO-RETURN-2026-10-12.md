# 共享语音回传与键盘残留复查

## 双方日志确认的情况

本轮输入是诊断格式 4、收集时间 2026-10-12T12:38:26Z 的双方报告。

- 两端请求与实际都是 RNNoise；浏览器 NS/AGC 关闭，非语音门控开启，没有处理器回退。
- 两端麦克风增益 150%、对方语音播放 200%。这些设置会放大残留；本轮不重置用户偏好。
- 共享者 Edge 155 的实际麦克风 AEC 为 `all`；观看者 Chrome 138 回退普通 AEC。
- 观看者发生 SFU → P2P 切换。旧报告的 `closed` 被记成 `other`，无法仅凭该日志确定退出原因。
- 当前采样共享者收到的语音区间丢包 16.36%、隐藏样本 8.85%；观看者收到的麦克风丢包 6.74%、共享音频丢包 3.37%。它们可能影响断续和清晰度，不能据此解释键盘残留。
- 用户确认：观看者的声音先在共享者端播放，再通过共享被传回。旧报告没有共享音频来源与自身音频排除实际设置，不能仅凭 RTP 判断数字回传与物理麦克风回声的比例。

## 本轮修改

共享采集检测 `restrictOwnAudio` 支持后请求 `true`；窗口音频偏好为 `window`，避免默认请求整个系统声音；选择器偏好排除本通话标签页。未禁用系统音频选项或本地游戏播放。浏览器可以忽略选择器偏好，因此以返回轨道的 `getSettings()` 为准。

双方诊断与共享右上角诊断增加 `共享音频采集`，含来源、轨道数、支持/请求/实际排除通话声音和风险说明。`实际排除通话声音: null` 表示未报告，不能写成成功。`true` 只表示浏览器报告已启用，真实声音隔离仍要试听。

输出诊断加入实际原生静音、Web Audio 放大、音频轨道数和重复播放风险。路由记录只在成员变化时记录发送路径变化；带宽预算仍照常更新发送器。收端主动退出记录画面持续卡顿、统计超时或 ready 失败的具体原因；服务端关闭保留安全原因白名单。

低音量 RMS 改为六位小数，避免静音残留一律四舍五入成 0。门控文案改为“非语音门控”，明确讲话时的键盘仍由 RNNoise 处理。本轮没有更换模型、叠加浏览器降噪或提高门控阈值，不能宣称讲话时键盘声已经解决。

机制参考：[W3C Screen Capture 工作草案](https://www.w3.org/TR/screen-capture/#dfn-own-audio-restriction)。`restrictOwnAudio` 处理本页面产生的共享音频，麦克风 AEC 处理扬声器进入麦克风的声音，两者分别诊断。

## 实机复测

1. 双方刷新页面，重新开始共享以使用新的采集请求。观看者连续讲话，共享者不讲话；观看者切换共享静音。如果回声随共享静音消失，主要来自共享音频；若仍存在，继续检查麦克风物理回声。
2. 复制双方诊断，核对 `共享音频采集.实际排除通话声音`。若为 false/null，优先选择独立视频标签页或游戏窗口的窗口声音；全屏系统声音可能仍包含通话声音。不要把未确认支持当成功。
3. RNNoise 下先不讲话打字，再边讲话边打字。临时将输入增益和对方播放各设 100% 作对比，并记录人声是否够响。随后可恢复偏好。
4. 保持讲话与共享，切麦克风、输出设备和降噪模式，检查最终选择、静音保持和游戏声音连续。新增共享采集选项不改变麦克风实时切换。
5. 需要继续改善讲话时键盘残留时，请用观看者听到的录音评估。门控更强可能吞掉首字和轻声；自动测试不能代替试听。

## 验证边界

单元测试验证支持检测、请求/实际状态分离、未报告回退、隐私白名单、原生与放大播放状态、SFU 日志及既有采集释放流程。真实浏览器双端自动测试验证 Socket.IO/P2P 诊断、200%合成音增益和全屏控制。它们不证明物理降噪、回声消除率或真实系统音频隔离效果。
