## 已确认并修复

| 优先级 | 问题与影响 | 修复及证据 |
| --- | --- | --- |
| P1 | PeerJS 接收无效 JSON、`null` 等消息会触发没有监听器的 `error` 事件，存在进程异常退出路径。 | 增加错误监听。隔离运行真实服务器，发送无效数据后，Socket.IO 请求及 HTTP 页面仍可正常响应。 |
| P1 | 挂断时尚未完成的语音加入请求，稍后可以重新写入房间归属，造成幽灵成员。 | 加入请求带每个 socket 的操作序号；挂断使旧请求失效。覆盖排队、成员查询、异步 join 三个阶段，以及同房间/跨房间竞争加入。 |
| P1 | 麦克风处理初始化期间先停掉旧音频；旧请求完成后还可能覆盖新处理器。重复请求或挂断也可能留下处理上下文。 | 整个采集与处理初始化作为一个受控操作；处理资源按流归属，完成后才接管，取消只清理自己的资源。四个回归场景在修复前全部失败，修复后通过。 |
| P1 | 切换设备时的旧失败请求会恢复旧选择，覆盖用户刚选的新设备；麦克风初始化后使用切换开始时的静音状态。 | 麦克风/摄像头选择增加操作序号，过期结果不更新 UI；新音轨使用最新静音意图。摄像头过期操作也不再覆盖当前错误状态。 |
| P1 | SFU 本地取消订阅后，服务器取消请求失败被吞掉；发布端可能继续抑制 P2P，而观看端已关闭 SFU。 | 取消失败进入服务器会话重置与 P2P 恢复流程。回归覆盖统计失败、接收完成确认失败和移除观看者。重置仍依赖信令服务可用；完全失联时不能保证新连接恢复。 |
| P2 | PeerJS 的 WebSocket upgrade 监听器同时处理 Socket.IO 路径，导致帧头错误与升级失败，持续使用轮询。 | PeerJS 使用 `noServer`，只接管自己的路径。真实服务器同时接受两种协议；完整浏览器联测的五个页面均确认实际 Socket.IO transport 为 websocket。此问题影响信令，不能据此认定它是全部视频低帧率的原因。 |
| P2 | 日志路径不可写或磁盘写入失败时，同步写日志异常会传到信令处理器。 | 写入失败降级 stderr，写盘恢复后自动恢复文件日志。用不可写目标验证不会抛出异常及恢复后能写入。 |
| P2 | 浏览器中保存的观看者音量若为有效 JSON 数字/字符串/数组，修改音量可能报错。 | 只接收对象形式的音量表；坏格式回到默认，明确保存的 0 音量仍保留。 |
| P2 | 浏览器禁用存储或容量满时，布局保存/清除抛错，界面可能仍提示成功。 | 存储方法返回失败结果；布局运行时显示准确提示，保留当前页面布局。阻止写入/清除的回归通过。 |

WebSocket 分路实现参考 [ws 官方的多服务共享 HTTP 示例](https://github.com/websockets/ws#multiple-servers-sharing-a-single-https-server)。

## 仍需处理或验收

1. **缺少 TURN。** `src/utils/iceServers.js` 只有 STUN；麦克风、摄像头以及屏幕的 P2P 恢复仍依赖直连穿透。在限制较多的 NAT 或网络中，即使页面和 SFU 可访问，P2P 也可能无法建立。需要配置经过认证的 TURN 服务及短期凭据，不能把普通 HTTP 反向代理当作媒体中继。参考 [WebRTC 官方 TURN 说明](https://webrtc.org/getting-started/turn-server)。本轮未新增服务或凭据。
2. **聊天发送确认不代表已持久化。** `ChatHistoryStore.append()` 在写盘失败时仍保留内存消息并返回；服务端随后返回 `ok: true`。当前语义证明消息被接受/广播，进程重启后可能丢失这部分消息。建议增加独立的持久化状态与失败提示，避免简单返回发送失败造成重复广播。同步写盘也可能在慢磁盘/高频聊天下阻塞信令线程；未做磁盘压力测试。
3. **日志没有轮转。** 本轮只修复写入失败不崩溃。持续写入的 `logs/node.log` 与 PM2 日志仍需服务器级大小监控和保留策略；没有自动删除日志或备份。未刷新服务器当前剩余磁盘数据。
4. **第三方前端加载依赖。** PeerJS 从 unpkg 加载，图标工具从 Font Awesome 加载。对应外部资源加载失败会影响功能或界面；可进一步把所需资源和许可固定到本地。没有将其认定为本轮实际卡顿根因。
5. **部署脚本的健康检查不足以证明 SFU 工作。** `deploy-baota.sh` 校验安装、HTTP 与文件路径，但 mediasoup 是可选依赖，安装失败后 HTTP 仍可通过。正式发布必须检查 native worker 和 SFU ready 状态，再验收双端音频及共享；不能只看 HTTP 200。1 GB 服务器应避免现场编译 worker，并保留匹配的旧依赖与回滚。
6. **资源与网络验收仍有边界。** 已有 SFU 接入预算、请求队列上限及资源保护；没有完成恶意连接压力、1 GB 服务器长时间负载、真实游戏编码或微信内置浏览器解码测试。高分辨率/60fps 目标不代表任何终端都能达到。重置请求也失败时，恢复取决于信令重连和服务端清理。
7. **直接 TLS 模式会在证书读取失败时退回 HTTP。** 反向代理部署通常使用 `USE_HTTPS=false`；若单独以 `USE_HTTPS=true` 运行，需要核对这一降级行为，避免把已启动误认为已提供 TLS。本轮未修改 TLS 配置或该兼容行为。
