# HTTPS 与媒体就绪检查（2026-10-22，本地候选）

## 完成内容

- `USE_HTTPS=true` 时必须成功读取并创建 TLS 服务，证书缺失、格式损坏或密钥不匹配均在监听前失败；不会改为 HTTP。错误输出只保留受限的系统错误码，不附加证书正文、私钥或配置路径。
- 支持成对配置 `TLS_KEY_FILE`、`TLS_CERT_FILE`，相对路径以项目根目录为基准。两项留空仍使用原有 `cert/selfsigned.key`、`cert/selfsigned.crt`。显式 HTTP 模式不读取证书。
- `/healthz` 保留 HTTP 200 的进程存活语义；新增 `/readyz`，媒体就绪返回 200，否则返回 503。响应禁止缓存，仅公开构建标识、媒体提供者和就绪布尔值，不导出 worker 统计、内部地址或成员信息。
- 传统模式检查 SFU 配置有效性；已启用的 worker 必须完成启动、仍存活且未处于资源异常状态。显式禁用 SFU 时允许 P2P 就绪；错误配置回退到 P2P 不会被标为就绪。Piik 模式继续探测其内部 `/healthz`，失败或超时均为未就绪。
- SFU 在初始化、失败、退出或关闭后准确报告未就绪；启动尚未完成时关闭服务，会释放迟到的 worker，启动失败时清理定时器和已创建资源。
- 宝塔部署脚本等待本机页面与 `/readyz`，再检查公网的页面和 `/readyz`。就绪检查要求 HTTP 成功且 JSON 的 `ok`、`mediaReady` 均严格为 `true`；503、HTML、错误字段、无效 JSON 或超大响应均失败。检查失败进入既有回滚流程，通过后才保存 PM2 配置。
- README 修正了已有测试命令和 `HOST` 实际绑定行为，发布文档补充证书配置与就绪验收。

## 后续：探测严格校验与 Windows 测试可靠性

后续媒体与设备修复的完整回归曾连续在部署门禁失败，出现 Git Bash `fork: Resource temporarily unavailable`、`0xC0000142` 或子进程超时。小范围探针确认：硬编码的 `C:\Program Files\Git\bin\bash.exe` 能执行内置命令和直接启动 Node，但管道与后续子进程存在间歇失败；PATH 中用户实际使用的 `C:\laragon\bin\git\bin\bash.exe` 则通过同样的管道探针。没有据此判定 Windows 全局资源耗尽，也没有修改 Git 安装、系统 PATH、进程限制或安全设置。

本次修改：

- `probe_ready` 改由单个 Node 进程直接完成 HTTP/HTTPS 请求与 JSON 校验，取消 curl→Node 管道。Node 已是部署脚本必需工具，没有新增运行资源、依赖或打包白名单。
- 要求响应状态**严格为 HTTP 200**，不跟随或接受重定向；仅 `ok === true`、`mediaReady === true` 通过。201、301 和 503 即使包含成功 JSON 也拒绝。旧 `curl --fail` 对 2xx/3xx 并不提供相同的严格状态码约束。
- 从请求开始设置 **8 秒总期限**，涵盖建连、TLS 和响应体接收；超时、截断、网络错误或超过 **65536 字节**都销毁请求并失败。上限按实际 Buffer 字节数计算，UTF-8 多字节正文也受限。恰好 65536 字节的合法成功 JSON 可以通过，65537 字节拒绝。
- 显式指定 `rejectUnauthorized: true`，拒绝不可信 HTTPS 证书，即使父进程设置了 `NODE_TLS_REJECT_UNAUTHORIZED=0`。测试中的自签名证书仅通过单个测试子进程的 `NODE_EXTRA_CA_CERTS` 临时信任，没有安装系统证书或全局关闭 TLS 校验。新探测使用 Node 的正常证书信任来源，直接请求目标，不使用 curl 的代理环境变量。
- Windows 测试按 PATH 查找已有 Bash；仅无匹配时才回退到原 Program Files 路径。没有跳过门禁，也没有扩大单次子进程的 20 秒观察上限。测试仍提取并通过实际 Bash 执行当前 `probe_ready`，不运行部署脚本主体。

验证结果：

- 实际 Bash + 本机 HTTP 响应矩阵 **14 个场景**、截断/8 秒超时、HTTPS 信任/继承不安全环境变量/拒绝连接/无效 URL 等场景通过，合计 3 项部署测试。新实现首次在原硬编码 Bash 中运行仍出现间歇 fork 失败；改用 PATH 中的 Bash 后，响应矩阵约 2.23 秒完成，各响应约 140–172 ms，整个专项约 11.59 秒，包含实际 8 秒期限检查。
- 随后的默认 **`npm test`：553/553 通过，0 失败、0 取消、0 跳过，约 12.24 秒**；没有设置测试并发限制。日志为本机临时目录的 `webrtc-readiness-probe-final.log`。之前 546/547、550/551 的失败记录仍保留在 [媒体与设备取消记录](MEDIA-CANCELLATION-2026-10-22.md)，属于修复前的验证结果。
- 定向 ESLint、差异空白检查与最终部署脚本 Bash 语法检查通过。没有修复或重装原 Program Files Git Bash；当前证据证明该测试选择可用 Bash 后通过，不代表另一套安装已恢复正常。
