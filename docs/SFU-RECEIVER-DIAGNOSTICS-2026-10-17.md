# SFU接收诊断增强：本地交付与后续定位

状态：仅本地修改，未部署、未连接生产服务器、未做浏览器手动验收。保留现有5fps/连续3次回退判定、120秒接收冷却、码率、编码器和关键帧恢复逻辑。自动化复现执行实际monitorSubscription释放路径，真实公网和双端实机由用户决定部署后验证。

## 保存与导出链路

现有约2秒一次consumer统计 → 最多8条/15秒的健康环形窗口 → 达到现有回退条件 → 释放订阅前复制整个窗口 → onReceiverFailure写入现有通话事件 → 页面已有存储逻辑 → 双方诊断导出与服务端白名单转发。

常规8条采样的首尾跨度为14秒，包含前面的正常采样和最后连续3次低帧，而非仅一条最终回退事件。如果共享刚开始即失败、统计读取耗时/超时或页面计时器被延迟，实际条数和时间跨度可能不足14秒；不补造缺失数据，也不为凑满窗口增加采样。

本轮核对补正：复制报告先等待本次采样完成，再读取健康窗口，确保复制过程中刚发生的回退不会只出现在事件里而顶层窗口仍旧。新增接收帧计数与RTC统计间隔，供重算比较；不调整原判定算法。

同一份“复制双方诊断”JSON中：

- 在观看端发起：`本机.SFU接收健康.最近回退[n].健康采样`。
- 在共享端发起：`对端[n].数据.SFU接收健康.最近回退[n].健康采样`，该对端应是实际观看者且状态为已采样。
- 双方都应出现 `SFU接收健康.接收健康格式 = 1`；共享者本身没有接收共享时，该端活跃接收和最近回退为空是正常的。
- 日志持久化位置：`当前会话.事件` 中类型 `SFU接收回退诊断` 的 `内容.健康采样`；刷新或开始另一通话后，旧窗口仍可在“通话日志”对应旧会话中找到。完整双方诊断只含当前会话，不自动带出旧会话。

## 下次只先回答三个问题

| 问题 | 优先读取的字段 | 判断边界 |
| --- | --- | --- |
| 服务器是否继续向该观看者发视频 | 服务器出站字节增长、服务器采样间隔_ms、服务器统计距接收_ms；同时看服务器入站字节增长 | 连续有效样本出站增长支持仍在转发；0表示该有效窗口不增长；null、过期、重复服务端时间戳均不能当作停止。服务器发包不等于观看端已经收到。 |
| 观看者是否收数据却不解码 | 接收字节增长、完整接收帧增长、解码帧增长、NACK/PLI/丢包/卡顿增长 | 有字节但0完整帧与有完整帧但0解码，是不同线索；不能仅凭一个窗口确定硬件、关键帧或网络根因。 |
| monitorSubscription低帧判定是否一致 | 解码帧数、完整接收帧数、解码帧增长、采样间隔_ms、接收统计间隔_ms、区间解码帧率、判定解码帧率、判定有效、统计对象变化、连续低帧次数 | 原监控用墙钟间隔计算判定帧率；RTC区间帧率用报告timestamp间隔。两种时钟或对象变化可能使数值不同；保留原始有限计数与两种间隔供核算，不改判定行为。 |

同一健康样本的收发/解码差分来自监控选中的同一条consumer统计；不包含transport中无关旧流的原始ID。不应与另一个页面播放器、另一条RTP流或不同采样区间直接相减。`停滞线索`仅是上述可见信号的概述，原字段优先。

服务端链路为 `src/server.js` → `src/utils/VoiceDiagnosticsRelay.js` → 上表共享schema。后两个文件不需要代码修改，但旧Node进程的ES模块缓存不会因磁盘替换自动刷新。因此未来需要配套替换4个文件，并在用户选定的维护时机重新加载对应业务Node进程；单纯复制文件或仅重启Nginx无效。重新加载业务进程可能打断当前信令/SFU会话，不能承诺在线共享无感恢复。本轮没有执行重新加载。

避免新旧混用的顺序：用户选定维护时机 → 备份4个原文件并记录SHA256 → 一并替换/核验4个文件 → 对应Node业务进程加载新schema → 双方刷新、重新进入语音并重新共享 → 用户收集双方JSON，核对格式标记和观看端完整窗口。现有版本仍为1.0.5，不能仅凭版本字符串判断本次增强已生效，应比较4文件SHA256及新字段。

若只能本机看到SFU接收健康、远端JSON中消失，先查服务端schema是否旧缓存或某端网页未更新；不要立即将字段缺失解释成无故障。若需要回滚，则同时恢复这4文件并让业务Node进程加载原schema，保留原.env、聊天数据及依赖。这里是用户未来部署的要求，不是已执行的步骤。

## 开销、隐私和自动化验证

- 不新增定时器频率、服务端统计请求或周期console输出，复用既有约2秒健康检查；只在现有回退发生时追加一条带窗口的通话事件。
- 每接收窗口最多8条且最多15秒；运行时最近回退最多3次；导出活跃接收最多8个。窗口不嵌入每个周期快照，避免反复复制。
- 导出仅允许有限数值、布尔和固定描述；没有RTP对象ID、publication/peer/device ID、地址、候选、SDP、用户名或音频内容。持有上一条原始RTC报告仅作内存差分，不写入日志/导出。
- 保持现有16000节点、16层深度等清洗预算，以及通话5会话/200事件/24历史样本、1200000字符本地保存上限。顶层健康窗口排在大历史之前，保护关键证据；超出事件上限时旧事件仍会按原规则淘汰，保存失败沿用原提示，不声称永久保存。
- 集成测试由实际监控产生3次回退，每次均检查8条/14秒窗口，经过日志、重新加载本地存储、真实relay与两端collectCombined序列化后逐项核对。未调用浏览器、麦克风、屏幕选择器或生产环境。
- 自动化另覆盖复制采样过程中的并发回退、满窗口与超大历史清洗预算、墙钟/RTC时钟不一致、后台/静止源、计数重置、统计超时和过期异步响应。三次完整回退窗口的测试数据小于64 KiB，简化双端集成JSON小于256 KiB；另有8活跃/3回退的边界清洗测试。这些是测试数据的体积检查，不是所有房间完整JSON的统一大小保证。
