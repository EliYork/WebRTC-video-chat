## 1.0.1 共享诊断验收

共享开始后，在共享窗口右上方展开“共享诊断”。默认收起，展开时才读取统计；等待至少两次采样再在模糊/卡顿发生时点击“复制脱敏诊断”。共享者与观看者各复制一份，以区分发送编码、带宽和接收解码问题。数据只复制到剪贴板，不上传服务器；复制失败可手动选中面板文本。

`null` 表示首次采样、缺少字段或浏览器不支持，不是零。码率和丢包率按相邻采样计算；发送端的丢包为远端反馈累计值，接收端另有区间丢包率。`none/cpu/bandwidth/other` 分别为未受限/算力/带宽/其他。诊断只读，不改变编码、码率或传输策略。真实双端画质仍需发布后验收。

### SFU 屏幕转发配置（30 Mbps 出口 / 1 GB 内存候选）

新实现保留语音和摄像头的 P2P 路径，屏幕视频与屏幕声音优先使用 mediasoup SFU。服务器只转发，不做视频转码。浏览器 SDK 和依赖许可证已放在 `src/views/vendor/`，属于现有 `src/` 白名单；服务器无需执行前端构建。

1. SFU 要求 **Node.js 22 或更新版本**。在新版本目录执行 `npm ci --omit=dev`。mediasoup 为可选依赖，安装或 worker 启动失败时回到 P2P；必须检查启动日志，不能把依赖安装成功等同于 SFU 已启用。安装优先下载平台对应的预编译 worker；若开始本机编译，1 GB 服务器可能内存不足，应在相同平台/架构的构建环境准备 worker，参考 mediasoup 的 `MEDIASOUP_WORKER_BIN` 配置，不上传 Windows 的 `node_modules` 到 Linux。
2. 在现有服务器 `.env` 中添加下列字段，将地址改成服务器的公网 IP：

   ```dotenv
   SFU_ENABLED=true
   SFU_ANNOUNCED_ADDRESS=服务器公网IP
   SFU_LISTEN_IP=0.0.0.0
   SFU_PORT=44444
   SFU_VIDEO_MBPS=22
   SFU_PAYLOAD_MBPS=23
   SFU_INITIAL_VIEWER_MBPS=5.5
   SFU_MEMORY_LIMIT_MB=700
   SFU_CPU_LIMIT_PERCENT=85
   ```

3. 云安全组与系统防火墙都放行 **44444/UDP 和 44444/TCP**。如果主机有 NAT，两个协议的外部端口都映射到同一内部端口。网站仍通过现有 HTTPS 反向代理访问；HTTP 反向代理不会转发这条媒体路径。SFU 使用 WebRTC 的 DTLS/SRTP 加密，无需额外把网站证书复制给 worker。
4. 正常启动日志应出现 `[sfu] ready on UDP/TCP 44444`。未填写公网地址、显式关闭、依赖缺失或启动失败时，页面仍可共享，但走 P2P。

**带宽与先到优先策略：**

- 默认游戏模式为 1080p60，“桌面文字”默认 30fps；两种模式的发送偏好都保持分辨率，不以主动缩小画面换帧率。浏览器会根据设备与网络调整压缩和实际帧率，目标值不是保证值。
- 22 Mbps 是共享者单份 SFU 视频的高上限，**不是固定码率，也不是每人 5.5 Mbps 的限速**。一两人观看时可按实际需要提高码率，仍受服务器 30 Mbps 物理出口限制。
- 所有频道共用 23 Mbps 媒体预算，为语音、协议开销、重传和其他项目留空间。`SFU_INITIAL_VIEWER_MBPS=5.5` 用于初始接入预估和编码起步，随后可提升到 22 Mbps。
- 已开始观看时保持 22 Mbps 视频编码上限，不再根据某个观看者的带宽估计或丢包主动压低整条共享流的码率。不提供低清层或手机降画质档位；浏览器自身的网络拥塞控制仍会决定实际发送码率。无人观看时释放上行预算，接入过程中短暂使用初始码率，开始观看后恢复高清上限。
- SFU 统计连接对象保持稳定，避免每秒重新创建连接标识而重置画质和诊断采样；诊断版本标识为 1.0.5。
- 每两秒从服务器读取发送源实际码率，并留 20% 估算余量。按观看订阅的先后顺序保留 SFU 路径，不为后来者平均削减已有观看者的码率；不足时，后来者自动走 P2P，仍可进入房间和观看。每 60 秒重新尝试可用 SFU 容量。
- SFU 只有一份编码流。本轮通过优先保留路径实现先到优先，没有为每个观看者生成不同画质。策略是应用层估算与接入控制，不是网卡硬限速；突发码率可能在两次采样之间短暂超预算。
- P2P 一两人且没有 SFU 上传时保留原 27 Mbps 高上限；多人或同时存在 SFU 上传时，扣除估计 SFU 上传后再分配直连视频预算。P2P 能否接入仍取决于网络穿透与共享者上行，无法保证任何网络下后来者都获得相同画质。
- CPU、Node 与 worker 内存峰值、系统剩余内存有保护阈值。连续三次资源采样超限会回到 P2P。1 GB 内存是否够用，需要在同时运行其他项目的真实服务器验证。
- 观看端收到并解码 SFU 视频后才停止其重复 P2P 发送。已连接的 P2P 视频 sender 保留空槽，SFU 或整个服务进程停止时可恢复发送；新加入者和需要重新协商的连接仍需要信令服务器恢复。
- 观看端每两秒检查实际解码进度。共享源仍在发送、页面在前台且连续三次低于 5fps 时，释放该观看者的 SFU 路径并恢复原始采集画面的 P2P，不降低分辨率或帧率目标。静止源、后台页面不据此切换；连续三次统计超时也恢复直连。同一共享两分钟内不重试 SFU，避免来回切换。
- 观看者诊断新增“观看路径”和所选媒体连接的 UDP/TCP 协议信息，便于区分服务器转发与 P2P；不导出候选地址。

## 回滚

停止新进程，将运行目录和启动配置恢复到记录的旧版本，再启动并检查。保留新版本日志以便排查。共享历史文件不要回退旧备份，否则会丢失发布后的聊天记录。如果未来涉及数据格式迁移，先制定兼容与恢复方案，不能只切代码目录。

旧版本目录和 ZIP 经确认后再手动清理，本地打包不会清理任何旧包。
