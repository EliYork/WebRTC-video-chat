# 聊天重连与发送确认（2026-10-22，本地候选）

## 已确认的问题

等待发送确认时发生断线重连，`rejoinCurrentRoom()` 会增加 room revision，使旧 Promise 的完成、失败与 finally 都不能修改新状态；但旧 `sending` 没有复位，发送按钮会持续不可用。另一个路径是浏览器 offline 后、重连前的旧成功确认仍会清空草稿。确认超时此前统一显示“发送失败，请重试”，无法准确表达服务器可能已接收消息的情况。

## 修复

- 连接离开 connected、或重新加入当前聊天时，释放待发送状态并使旧回调失效；在离线期间保持按钮禁用，连接恢复后正常使用。
- 对结果不明的发送保留原输入，提示先核对聊天记录，避免重复发送。断线状态优先展示连接提示，重连后仍可看到待核对提醒；保存状态不能覆盖待核对提醒。开始新的发送或编辑输入后解除该提醒，切换频道时清除旧频道提醒。
- Socket.IO 超时、断线或无效确认标记为 `deliveryUncertain`；明确 `ok: false` 的拒绝继续显示发送失败。成功确认与写盘状态仍分别处理。
- 旧请求的成功、失败和 finally 都不能清空新草稿、显示过时错误或解锁新的待发送请求；没有新增自动重发、客户端消息 ID 或服务端去重协议。

## 后续：切换频道与重连后等待当前历史

原实现选中频道后立即允许发送，服务端可能尚未完成加入；快速 A→B→A 时，第一次 A 的迟到历史又会因频道 ID 相同被接纳。同频道重新加入也存在旧历史提前解锁发送的路径。所有选择还会逐个排队，导致已经放弃的中间频道继续请求。

### 修复与约定

- `chat-panel-runtime.js` 在当前历史完成前禁用发送按钮，并在 Enter 和直接提交入口再次检查；输入仍可编辑。断线后重新等待历史，离线历史不能解锁发送，已有消息与草稿保留。
- 每次选择及重新加入传递前端本地 `requestRevision`，历史返回时同时核对频道和 revision，拒绝同频道的过期历史。等待期间收到的当前频道实时消息保留，合并历史时按 ID 去重。
- `chat-socket-transport.js` 保留一个正在等待历史的请求和一个最新待发选择，取代尚未发出的中间选择。已经发出的请求仍等待对应历史完成，再发送最新选择。
- 两个前端模块必须一起更新。`chat:join` 线上载荷仍仅为 `{ roomId }`，没有修改服务端或增加请求 ID 协议；本地 revision 关联依赖现有串行历史响应约定，手动/旧适配器仍允许省略 revision。
- 未新增加入超时或自动重试。若历史响应始终不返回，发送保持禁用、草稿保留；本轮不宣称解决这种等待，也没有自动重发消息。

## 后续：重叠历史与实时消息按流顺序合并

### 问题与修复

服务器只返回最近 50 条历史，而页面可保留 500 条。等待历史期间，实时队列可能包含快照之前的消息、快照内的消息及快照之后的消息。此前直接拼接“历史 + 实时”再去重，会把快照中已被裁掉的较早实时消息放到末尾；合并超过 500 条时，还会误裁较新的历史行。

`chat-panel-runtime.js` 用历史与实时消息共有的稳定 ID 找到边界，将较早的实时前缀放在快照之前，再合并快照和剩余实时事件、去重并裁剪。快照中的消息内容继续优先，服务端顺序保留；不按 `createdAt` 排序，因此不依赖时钟单调或时间戳精度。没有共有 ID 时沿用历史在前的行为，不声称可以推断两个不相交记录段的完整顺序。无 ID 消息仍不做强去重。
