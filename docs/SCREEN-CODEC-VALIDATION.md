# 屏幕共享编码器第一阶段：H.264 与 VP8

## 当前实现

只对屏幕共享视频选择编码器，复用原有采集、发送策略、共享诊断和 SFU/P2P 路由。语音和摄像头不做编码器预检测。H.265、AV1 没有启用，版本号没有改变。

共享设置的“高级设置”提供：

- 自动：按实际捕获尺寸及所选帧率运行本地 H.264 动态画面测试，合格则优先 H.264；不支持、失败、数据不足或超时则选 VP8。
- H.264 优先：仍执行检测并保留结果，但允许手动越过性能门槛；浏览器/SFU/对端不兼容时允许 VP8 回退。以诊断中的实际编码为准，不宣称每条连接都使用 H.264。
- VP8：跳过 H.264 检测，作为基准对照。

这些设置在停止后重新开启共享时生效，不在共享过程中切换编码器。编码器选择和检测结果仅属于本次共享，不缓存成设备永久能力。

## 预检测边界

`voice-screen-codecs.js` 中的启用编码器表集中声明 MIME、格式匹配、自动选择顺序、检测函数及兼容回退；SFU 和 P2P 使用同一个选择结果。后续验证新编码器时增加对应描述和探测，不需要再建立一套选择或路由系统。

检测使用两个无 STUN 的本地 RTCPeerConnection、同尺寸动态 Canvas、实际 H.264 协商及 RTCStats。不会请求摄像头/麦克风，不把屏幕内容传给检测连接，也不经过业务服务器。普通捕获大于4K时检测记为不确定，自动模式回退 VP8，不缩小画面后冒充通过。

预热后取两个连续约1秒窗口：采集及编码进度均达到目标的95%，编码尺寸保持目标尺寸且实际编码为 H.264，才通过。1080p60 的门槛约57fps，50fps不会通过；计数缺失、流切换、分辨率下降、采样窗口异常均不算通过。检测最长6.5秒，超时或取消会关闭连接、停止检测轨道、清理计时器；挂断或浏览器结束采集不能把过期结果发布出去。

测试表明的是这次本地动态画面的发送编码能力；不证明真实游戏负载、采集设备、SFU公网或观看端解码能维持同样帧率。能效报告不证明硬件编码器身份。保持 `maintain-resolution` 和发送缩放1，不以自动降低分辨率换取通过。

## 与传输链路的接入

- SFU使用 mediasoup 的显式 `codec` 选项。H.264 格式要求 packetization-mode=1；没有兼容 H.264 则选 VP8。明确的 H.264 不支持错误允许在同次发布中重试 VP8一次，网络/会话失败仍使用原有P2P恢复逻辑。
- P2P在PeerJS首次Offer的 `sdpTransform` 边界应用偏好，保留H.264之后的VP8及关联RTX，避免在首次Offer已经生成后才设置偏好。新观看端通过可选呼叫元数据在Answer沿用同一偏好；旧观看端仍按普通协商处理。音频段不改。VP8模式只保留VP8及关联RTX。
- 摄像头与共享之间、不同编码器之间需要新Offer，单纯 `replaceTrack` 不能改变已协商编码器；相同编码器的媒体更新仍复用原有轨道替换。
- SFU不会转码。不能接收其已发布编码格式的观看端仍可能使用P2P兼容路径；不会为此降低所有观看者的分辨率。

## 启动码率：目前能确认什么

原代码对SFU发布固定设置 `videoGoogleStartBitrate: 1500`，单位kbps。新默认不发送该提示，交给浏览器；高级设置保留1.5Mbps、5.5Mbps两档供对照。提示受本次发布码率上限约束，诊断显示真正传入的值；它不是恒定码率或最低码率。

已有SFU资源策略仍会在无观看端、观看端尚未就绪、已有就绪观看端之间调整发送上限；此策略与启动提示是两个不同因素。参数读回会显示当时的实际上限。自动测试只验证选项和参数接入，不证明移除1.5Mbps提示已缩短爬升。

此前“1080p60约50fps”的现象还没有本轮同步实机样本，无法确定唯一根因。现已具备分阶段采样能力，按下表定位。

## 实机对照步骤

1. 共享者和观看者刷新页面。保持相同浏览器版本、机器、窗口大小、1080p60、共享内容模式及观看人数；先用一个观看者。选择同一个持续运动画面，每轮至少30秒。避免以静止桌面判断帧率。
2. 先选VP8、SFU启动码率“浏览器默认”，开始共享。双方展开“共享诊断”，至少等两个采样周期；分别在开始后约5、15、30秒复制诊断，记下所在轮次。
3. 停止共享，改为H.264优先，重复相同画面与时段。核对双方实际编码字段确实为 `video/H264`；若回退VP8，记录该轮为兼容回退，不能拿它作为H.264性能样本。
4. 再选自动模式，查看“编码器选择”的目标、检测结果和两个窗口。失败原因 `probe-source-slow` 是测试画面产生不足，`encoder-slow` 是编码输出不足，`missing-stats` 是不能判定；不是对真实屏幕捕获或硬件型号的结论。
5. 固定一种编码器，再分别测试“浏览器默认 / 1.5Mbps / 5.5Mbps”的启动提示，保持观看路径和其他条件一致，比较5、15、30秒的帧率、实际码率、目标码率和发送等待。先比较一项，再比较下一项。
6. 检查共享音频及麦克风、停止共享恢复摄像头、退出重进、共享重开、观看路径转为P2P后的音画和实际编码。无需修改服务器能力或全局关闭SFU来开始编码器对照；若已有路径切换测试条件，可额外比较P2P轮次。

实际码率由编码器与拥塞控制决定，即使固定同一上限，H.264与VP8也未必使用相同码率。因此第一阶段应同时记录实际码率；QP只适合同编码器内比较，不能用H.264与VP8的QP数值直接判优。

## 如何分辨50fps出现在什么阶段

诊断格式升级为3，仍保留旧帧率、丢包、QP、抖动、缓冲等待和编解码时间字段。

| 同一持续运动画面的表现 | 下一步检查 |
| --- | --- |
| 采集区间约50，编码与发送也约50 | 实际屏幕捕获、浏览器调度、源帧率；提高发送码率无法补出未采集帧 |
| 采集约60，编码约50 | 预检测结果、编码器负载、编码受限原因、目标码率与实际参数 |
| 编码约60，发送明显低或每包等待增加 | 上行发送、重传和拥塞适配 |
| SFU入站正常、出站低，观看端完整收帧也低 | 服务器至观看端链路、SFU分配或转发；需结合两端同一时段数据 |
| 完整收帧约60，解码约50 | 观看端解码/资源占用；查看解码耗时与丢帧 |
| 解码正常，提交合成器明显低 | 播放、渲染、页面后台状态；该值不等于显示器扫描输出 |

SFU服务器统计只导出入站/出站视频码率、累计字节、包数、可用的丢包计数及采样时间；未知字段为null，不伪造服务器帧率。不导出IP、候选地址、SSRC或连接标识。发送参数核对显示请求、浏览器当前接受值及不一致字段；`applied`仅表示调用完成，仍需看不一致字段和实际媒体输出。
