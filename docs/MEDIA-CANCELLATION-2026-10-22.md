# 媒体请求取消与重试（2026-10-22，本地候选）

## 问题与修复

媒体控制器以 token 区分每种媒体的新旧请求，以语音会话 epoch 判断请求是否仍然有效。此前仅在成功返回媒体时检查 epoch；请求因为 epoch 变化而过期后，虽然会停止返回的轨道，却没有清除自身的 pending Promise，后续请求会一直复用已经结束的取消结果。旧请求拒绝时也没有检查 epoch，可能把旧设备错误写入当前状态。

`src/views/js/voice/voice-media-operation-runtime.js` 现在在执行操作前、成功返回后和失败时使用相同的有效性检查。已经取消且尚未开始的操作不会调用媒体获取；已经开始的请求若迟到返回，会继续清理其结果。取消只释放该 token 仍拥有的 pending 状态，不会清除新请求；已有媒体值保留为 active，没有媒体值则回到 idle。旧请求错误作为取消处理，不再生成当前设备故障。

摄像头和麦克风原有的 `surviveEpochChange: true` 继续生效，单纯的传输连接变化不会取消它们；显式 invalidate、dispose 或 token 替换仍会取消。屏幕请求继续使用 `surviveEpochChange: false`。

`src/views/script.js` 配套记录屏幕操作是否真正开始。切换屏幕来源时，调用方可能已经取得一条 preparedStream；如果控制器在执行前取消，该流尚未交给操作处理，调用方负责停止。已经开始的操作沿用自身清理路径，避免重复清理。此修改没有改变媒体质量、共享协议或重建通话策略。
