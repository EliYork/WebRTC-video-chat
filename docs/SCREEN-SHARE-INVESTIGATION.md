# 屏幕共享画质与帧率排查

## 当前工作区更新（2026-10-09）

已增加可选 mediasoup SFU，屏幕视频和屏幕声音优先由服务器转发，语音/摄像头继续 P2P。游戏默认 1080p60、motion / maintain-framerate；桌面文字保留清晰度优先模式。

当前按实际码率估算全局出口预算，先到的观看订阅优先保留 SFU，后来者容量不足时仍可通过 P2P 观看。一两人不再采用固定 5.5 Mbps 上限：默认单份 SFU 视频高上限为 22 Mbps，全频道媒体预算为 23 Mbps；5.5 Mbps 只用于初始容量估算。配置和验证边界见 [RELEASE.md](RELEASE.md)。

以下是 2026-09-10 的历史诊断与改动记录，不能当作当前传输拓扑或新方案的公网验收结果。

## 当前工作区：30 Mbps 路径的清晰度优先候选策略

- 取消按采集尺寸和低帧率折扣设置的 2.6–24 Mbps 上限；每条共享视频发送上限统一为 27 Mbps，保留 detail / maintain-resolution / scaleResolutionDownBy=1。这是待实测的上限，不是最低码率或恒定码率，不保证原始分辨率或60fps。
- 不改变用户所选采集帧率和分辨率；需要高帧率请选择60fps，超过1080p的源需要选择原始分辨率或相应档位。低帧率不再连带压低码率预算。
- 当前只有STUN、没有TURN/SFU，视频是浏览器之间传输；服务器30 Mbps上传、50 Mbps下载不是这条媒体路径的预算。不能通过发送参数让信令服务器上传吃满。
- 27 Mbps为每个发送流的上限，不是多人合计限额；多观看端会争用共享者上行。保留拥塞控制，预留的3 Mbps也不是对重传开销的保证。若需利用服务器中转，另行设计TURN/SFU及多人总带宽分配。
- 验收用相同动态画面、60fps采集，检查双端实际发送码率、分辨率、编码/发送帧率、QP、丢包和受限原因。静止画面低码率正常；本地自动测试不证明公网画质和帧率改善。

## 第一轮修复

只标记屏幕捕获轨道；使用motion提示、maintain-framerate降级偏好，允许浏览器在不足时降低分辨率而不是坚持4K却大量降帧。按真实捕获尺寸配置720/1080/1440/4K档最大码率4/8/14/24Mbps（60帧档；30帧及以下乘0.65），设置所选最大帧率和发送缩放1。

这些是待实测的策略值，不是已验证的最优值。maxBitrate仅是上限，不强迫浏览器消耗带宽，也不关闭拥塞控制，不保证4K60或解决全部卡顿。不改SDP、不强制编码器、不影响音频。首次呼叫、连接成功及轨道替换重新应用；按sender串行设置，参数不支持时捕获异常，切回普通视频时恢复原发送参数。

## 验证边界与下一步

### 用户要求取消降分辨率策略

在1.0.4之后的本地修改中，将motion/maintain-framerate改为detail/maintain-resolution，优先保持分辨率。保留码率上限、所选最大帧率、缩放比例1和参数去重。资源不足时可能降低帧率；这是浏览器适配偏好，不是任何条件下都能保证原分辨率的承诺。首次启动或重开共享后应用新策略，尚未打包或双端验收。

### 1.0.3 后续反馈与窄修复

用户反馈已明显顺畅；新快照采集约31、本地合成32、发送32fps，实际11.13Mbps、QP2.97。与旧快照内容/时刻不一致，不作严格改善幅度比较；尚不能确认采集约32fps的具体原因。

保留现有码率与降级策略。发现连接状态与ICE状态都可能触发相同setParameters，改为比较浏览器当前参数，仅在策略字段发生变化时写入，仍允许重协商后修复。共享预览重复同步会调用attachAndPlayMedia，原实现无条件重赋srcObject并play；改为相同流不重复赋值，已播放不重复play，暂停/强制重绑仍可恢复。这些是减少冗余操作的代码修复，不宣称已证明它们造成此前32fps，也不承诺固定60fps。

自动测试覆盖参数计算、生命周期接入、普通轨道不改及恢复、错误兼容。真实双端验收未完成。相同移动窗口动作对比编码/发送帧率、QP和丢包；若仍低帧率，继续核对浏览器实际参数和编码内部限制，不宣称已找到2.24Mbps目标的唯一原因。已有诊断和窗口按钮修复保留；本轮不自动改版本或部署。
